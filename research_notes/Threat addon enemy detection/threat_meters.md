## Q1: Which meters track only target/focus/targettarget, and which showed several mobs at once? How did the multi-mob ones find enemies?

### Takeaway
Every mainstream meter (KTM, Omen3, TC2, Details Tiny Threat, Skada) shows one mob's threat list across the group. It picks that mob from a short fixed list of unit tokens: target, then targettarget, with focus/focustarget optional. None of them enumerates nameplates. The multi-mob views come from niche or tank addons. Lazy Threat reads every enemy nameplate. TankThreatTracker caches per-GUID readings taken from target/mouseover and uses CLEU plus nameplates only to decide whether a cached mob is still alive and fighting. TWThreat gets a per-mob list from a custom server API. So nameplate scanning is the only way found to read live threat on mobs nobody is targeting.

### Cited Findings
- **Omen3 (WotLK 3.0+ through retail/Classic ports)** picks exactly one mob. `FindThreatMob()` walks `{"target","targettarget"}`, or `{"focus","focustarget","target","targettarget"}` with the UseFocus option. It takes the first unit that exists, is not a player, can be attacked and has health > 0, and can skip player pets (`Omen.lua` L1730-1758). The title text is set to that mob's name. [Omen source (WowAce git)](https://www.wowace.com/projects/omen-threat-meter/source)
- Omen3 polls when the mob is targettarget, because no event fires for it: "Schedule a repeating timer for updating threat on 'targettarget' since we get no events on a targettarget change" with `ScheduleRepeatingTimer("UpdateBars", 0.5)` (L1811-1815). The timer is cancelled on PLAYER_TARGET_CHANGED (L1285-1291). [Omen source](https://www.wowace.com/projects/omen-threat-meter/source)
- Omen's own description says the API only answers for units the group is targeting: threat details can't be obtained unless somebody in your party or raid is targeting the mob. [Omen on CurseForge](https://www.curseforge.com/wow/addons/omen-threat-meter); [WowAce project page](https://www.wowace.com/projects/omen-threat-meter)
- **ThreatClassic2 (2019 to now)**: "Threat list for your target including party/raid members." On Classic clients, `UpdatePlayerTarget()` uses `"target"` if it is hostile. Otherwise it uses `"targettarget"` if that is hostile (healer mode). On mainline/Forever it is forced: `-- mainline returns secret threat values for targettarget` / `if isMainline or isForever then TC2.playerTarget = "target" return end` (core.lua L727-739). [TC2 core.lua](https://github.com/dfherr/ThreatClassic2/blob/9f4a4c3592ef31f15e8ef1a4cb708d8bda3e2fbe/core/core.lua#L727-L739); [TC2 README](https://github.com/dfherr/ThreatClassic2/blob/master/README.md) ("Healer mode (target of target) is not available. Target the enemy directly to see its threat list.")
- **Details! Tiny Threat** describes itself as a "Small tool for track the threat you and other raid members have in your current target." `GetUnitId()` returns `"focus"` if the usefocus option is on and focus exists, otherwise `"target"` (Details_TinyThreat.lua L33, L282-293). It refreshes on a repeating timer (`ScheduleRepeatingTimer("Tick", updatespeed)`, default 1 s, L759/L960). [Details_TinyThreat.lua](https://github.com/Tercioo/Details-Damage-Meter/blob/2efa4b10628e0e4a91c346138cf8325e81d0a43c/plugins/Details_TinyThreat/Details_TinyThreat.lua)
- **Skada (modern, has Forever TOC)**: `find_threat_target()` returns `"target"` if hostile. With the option on it falls back to `"focus"` and then `"focustarget"`, and finally to `"targettarget"` when the target is friendly (modules/Threat.lua L25-38). The window title is the mob's name, replaced by the mode name if `issecretvalue(targetName)`. [Skada Threat.lua](https://github.com/zarnivoop/skada/blob/1da7ee7d4144e25384f01bf80b8436e7afc6951c/modules/Threat.lua#L25-L38)
- **Skada-WoTLK** uses the same Omen-style list: `local threatUnits = {"focus", "focustarget", "target", "targettarget"}` (Skada/Modules/Threat.lua L607). [Skada-WoTLK Threat.lua](https://github.com/bkader/Skada-WoTLK/blob/master/Skada/Modules/Threat.lua)
- **KLHThreatMeter R17 (vanilla 1.12)** has no per-mob view at all. Each player has one running threat total: `me.raiddata = { } -- raid's threat table data`, `getraidthreat()` returns the "total" threat plus an offset, and `resetraidthreat()` zeroes it (KTM_Tables.lua L7-8, L100-114). To limit counting to one mob, a raid officer runs `/ktm mastertarget set`: "If you set up a master target, then any damage and abilities against other mobs will not register on the meter." [KTM_Tables.lua (SVN mirror)](https://svn.grimore.org/vanilla-wow-addons/k/KLHThreatMeter/Code/KTM_Tables.lua); [Advanced Raid Commands.txt](https://svn.grimore.org/vanilla-wow-addons/k/KLHThreatMeter/Readme/Advanced%20Raid%20Commands.txt)
- KTM readme: "The mod records your own threat and sends updates into a shared channel. Other players in your raid who are also using the mod will pick up the messages and see you in their raid threat window." [KTM Readme.txt](https://svn.grimore.org/vanilla-wow-addons/k/KLHThreatMeter/Readme/Readme.txt)
- **TankThreatTracker / "Threat Watcher" (Classic Era 11403, 2026)** is a multi-mob view. It reads threat only from `UnitDetailedThreatSituation("player","target")` and `("player","mouseover")` and caches each reading by GUID in `threatCache`. COMBAT_LOG_EVENT_UNFILTERED marks hostile NPC GUIDs as in combat. `IsValidCombatUnit()` keeps a cached row while the GUID matches an in-combat `target`, `mouseover` or `nameplate1..40`, or while the cache or tracked-unit timeouts haven't expired (TankThreatTracker.lua L281-316, L337-370). So the numbers for mobs you aren't targeting are stale snapshots. The CurseForge page says: "Classic wow makes it very difficult to track multiple enemy units at the same time." [TankThreatTracker.lua](https://github.com/mathis1337/TankThreatTracker/blob/main/TankThreatTracker.lua); [Threat Watcher on CurseForge](https://www.curseforge.com/wow/addons/tank-threat-watcher-tracker)
- TankThreatTracker's header records the same secure-targeting wall FireThreat hits: "TargetUnit() from a non-secure click is forbidden; SetAttribute() on secure buttons is blocked in combat (even from PreClick); secure type="target" with unit="nameplateN" silently fails; and "/target nameplateN" macros treat the token as a literal name. Instead, we GLOW the nameplate of any at-risk mob." (L4-15). [TankThreatTracker.lua](https://github.com/mathis1337/TankThreatTracker/blob/main/TankThreatTracker.lua)
- **Lazy Threat** (Retail first, plus MoP Classic, TBC Classic, Classic Era/SoD/HC) is an "AoE threat meter for Retail: reads threat from every enemy nameplate." Every visible enemy nameplate gets a numbered priority overlay, scrollable bars list every mob in combat, and party/raid frames show threat on each member's target. A "Threat accuracy (1-8)" setting controls how many target-chain levels are checked. Enemy nameplates must be enabled. Source not inspected. [Lazy Threat on CurseForge](https://www.curseforge.com/wow/addons/lazythreatbyloafs)
- **Classic Threat** (Classic / TBC Classic, last update 2023): "Unlike other threat addons, ClassicThreat tracks multiple surrounding enemies" and shows threat on unit frames. It calls itself a proof of concept with API limitations. The page doesn't say how it enumerates enemies. [Classic Threat on CurseForge](https://www.curseforge.com/wow/addons/classic-threat-classic-tbc-classic)
- **TWThreat (Turtle WoW)** has a "tankMode" that gets a per-creature list from the server. Packets prefixed `TMTv1=` carry `creature:guid:name:perc` entries, which are stored in `TWT.tankModeThreats[guid]` (TWThreat.lua L26, L797-830). [TWThreat.lua](https://github.com/CosminPOP/TWThreat/blob/master/TWThreat.lua)
- Other multi-target meters showed up in search but weren't inspected: Kalimo Threat (Classic Era/HC, "multi-target panels") and NKThreat (TBC Classic, "multi-target threat grid"). [Kalimo Threat](https://www.curseforge.com/wow/addons/kalimo-threat); [NKThreat](https://www.curseforge.com/wow/addons/nkthreat)

### Inferences
- The big meters all show one mob, because Blizzard's API answers per (unit, mob) pair and needs a mob unit token. The meters chose the cheapest tokens that always name the mob the user cares about. The multi-mob addons get extra mob tokens from nameplates (Lazy Threat), mouseover plus caching (TankThreatTracker) or a server-side API (TWThreat).
- Of the client-API addons found, live per-mob numbers for mobs nobody is targeting come only from nameplate tokens. raidNtarget/partyNtarget only reach mobs some group member is targeting, and mouseover/cache only gives snapshots. A nameplate approach like FireThreat's is therefore the standard technique for a tank's "all mobs on me" list, not an oddity.

### Gaps
- No source was read for Lazy Threat, Classic Threat, Kalimo Threat or NKThreat. CurseForge descriptions don't show whether they loop nameplate1..40 or use NAME_PLATE_UNIT_ADDED, or which threat calls they use.
- No primary source was found for **Omen2 / Threat-2.0** (TBC, 2007-2008) or Threat-1.0. Searches returned nothing useful. LTC2 credits "Chris Heald and the Threat-1.0/Threat-2.0 teams" and keeps their per-player, per-mob-GUID table design (see Q4), but whether Omen2's UI ever listed several mobs at once is unverified.
- Later KTM versions (TBC-era R18+) weren't checked. Findings apply to R17 (vanilla 1.12).

## Q2: Did any meter scan partyNtarget / raidNtarget to discover mobs?

### Takeaway
Omen3 builds raidNtarget/partyNtarget tokens, but only as the *unit* argument. They pick up threat-table entries for things the raid targets that aren't raid members, such as NPC tanks. The mob itself still comes from target/targettarget/focus. KTM (vanilla) scanned `raid1..40target` only to find world bosses for special boss events and spell reporting. The only addon found that uses group targets to show threat on more mobs is Lazy Threat ("party/raid frames show threat for each member's target"), and its source wasn't verified.

### Cited Findings
- Omen3 builds `ptID[i] = format("party%dtarget", i)`, `pptID[i] = format("partypet%dtarget", i)`, `rtID[i] = format("raid%dtarget", i)` and `rptID[i] = format("raidpet%dtarget", i)` (Omen.lua L219-232). In `UpdateBarsReal()` they are called as `updatethreat(rtID[i], mob)`, i.e. `UnitDetailedThreatSituation("raidNtarget", mob)`, next to `rID`/`rpID`. The same function also calls `updatethreat(mobTarget, mob)`, `"mouseover"` and `"mouseovertarget"` (L1830-1862). Omen's comment explains the mobTarget call: "We want the mob's target just in case the tank isn't in our raid (say an NPC or some other player)". Results are deduplicated by GUID through `threatTable[guid]`. [Omen source](https://www.wowace.com/projects/omen-threat-meter/source)
- Omen3 also passes raidNtarget tokens to `recordThreat(unitID, rtID[i], srcGUID)` inside its COMBAT_LOG handler (L1578-1588). That path records threat for Mirror Image/Fade/Tricks/Misdirection, where the API temporarily reports 0 or misattributes threat. [Omen source](https://www.wowace.com/projects/omen-threat-meter/source); [Omen on CurseForge](https://www.curseforge.com/wow/addons/omen-threat-meter) (it says it doesn't estimate threat except for Tricks, Misdirection, Mirror Image, Fade and glyphed Hand of Salvation)
- KTM R17 loops `for x = 1, 40 do ... UnitClassification("raid" .. x .. "target") == "worldboss"` to find Azuregos for a threat reset and the Twin Emperors for a threat gain (KTM_Bosses.lua L95-104, L476-500). It also matches `UnitName("raid" .. x .. "target") == me.mastertarget` for spell reporting (L228-235). [KTM_Bosses.lua](https://svn.grimore.org/vanilla-wow-addons/k/KLHThreatMeter/Code/KTM_Bosses.lua)
- TC2, Details Tiny Threat and Skada loop `raidN`/`partyN` (plus pets) only as units against one mob token. TC2: `UpdateThreatData(TC2.raidUnits[i])`, `UpdateThreatData(TC2.raidPetUnits[i])` (core.lua L748-766, units built at L1592-1603). Skada: `format("%s%d", groupType, i)` and `"%s%dpet"` (Threat.lua L121-131). Details: `"raid"..i` / `"party"..i` (L335-361). [TC2 core.lua](https://github.com/dfherr/ThreatClassic2/blob/9f4a4c3592ef31f15e8ef1a4cb708d8bda3e2fbe/core/core.lua); [Skada Threat.lua](https://github.com/zarnivoop/skada/blob/1da7ee7d4144e25384f01bf80b8436e7afc6951c/modules/Threat.lua); [Details_TinyThreat.lua](https://github.com/Tercioo/Details-Damage-Meter/blob/2efa4b10628e0e4a91c346138cf8325e81d0a43c/plugins/Details_TinyThreat/Details_TinyThreat.lua)
- Lazy Threat: "Party and raid frames show threat for each member's target", plus a "target chain" depth setting (1-8 levels). [Lazy Threat on CurseForge](https://www.curseforge.com/wow/addons/lazythreatbyloafs)

### Inferences
- Scanning group members' targets could find extra mobs in a raid. It misses every mob nobody targets, though, which in a tank's AoE pack is most of them, and the user's background says Forever restricts compound tokens like targettarget (see Q3). Nameplates are the broader source.

### Gaps
- It wasn't tested whether `raidNtarget` / `partyNtarget` tokens return readable or secret values on Forever. TC2's comment covers only `targettarget`.

## Q3: In the native-API era, which calls, events and unit arguments do meters use? (incl. Forever/mainline secret-value handling)

### Takeaway
All native-API meters call `UnitDetailedThreatSituation(groupUnit, mobUnit)` once per group member/pet for one mob token. Omen also registers both UNIT_THREAT_LIST_UPDATE and UNIT_THREAT_SITUATION_UPDATE, while TC2 registers only UNIT_THREAT_LIST_UPDATE. Polling covers targettarget, which fires no events. Two maintained meters now ship Forever builds (TC2 with interface 16001, Skada with Skada_Forever.toc), and both *read and do arithmetic on* UnitDetailedThreatSituation numbers with `"target"` as the mob. TC2 says only `targettarget` returns secret values on mainline/Forever. Secrecy may therefore depend on the mob token, and FireThreat should test whether `"target"` gives readable numbers where `nameplateN` doesn't.

### Cited Findings
- **Omen3 events**: `RegisterEvent("UNIT_THREAT_LIST_UPDATE")`, `RegisterEvent("UNIT_THREAT_SITUATION_UPDATE")`, `PLAYER_TARGET_CHANGED`, `UNIT_TARGET`, `GROUP_ROSTER_UPDATE`, `UNIT_PET`, `COMBAT_LOG_EVENT_UNFILTERED` (Omen.lua L610-632). Every handler just throttles into `UpdateBars()`. Omen's 2008-era comment on UNIT_THREAT_LIST_UPDATE: "It appears that unitID can only be 'target' or 'focus'" (L1272-1275). On UNIT_THREAT_SITUATION_UPDATE: "this only triggers when major state changes, not when the raw threat values change" (L1277-1283). [Omen source](https://www.wowace.com/projects/omen-threat-meter/source)
- Omen3's in-code API notes (L1662-1693): `state = UnitThreatSituation(unit, mob)` returns nil if the unit isn't on the list, 0 for 0-99% raw, 1 for 100%+ raw, 2 for tanking but insecure, 3 for securely tanking. `UnitThreatSituation(unit)` with no mob returns "the unit's maximum threat state on any mob's threat list". `UnitDetailedThreatSituation(unit, mob)` returns `isTanking, state, scaledPercent, rawPercent, threatValue`. `GetThreatStatusColor(state)` returns the UI colors. Omen itself only calls the detailed function: `updatethreat(unitid, mobunitid)` (L1712-1728). [Omen source](https://www.wowace.com/projects/omen-threat-meter/source)
- Omen3 draws its pull-aggro line with range checks rather than the API's scaled percent. It uses `IsItemInRange(37727, mob)` (5-yard Ruby Acorn) or item 8149, choosing a 1.1 or 1.3 multiplier (L1866-1871). [Omen source](https://www.wowace.com/projects/omen-threat-meter/source)
- **TC2 events**: `PLAYER_ENTERING_WORLD`, `GROUP_ROSTER_UPDATE`, `ZONE_CHANGED_NEW_AREA`, `PLAYER_TARGET_CHANGED`, `UNIT_TARGET` (only on non-mainline/non-Forever, "target"), `PLAYER_REGEN_DISABLED/ENABLED`, `UNIT_THREAT_LIST_UPDATE`, and `ENCOUNTER_START/END` on mainline/Forever (core.lua L1559-1580). Its UNIT_THREAT_LIST_UPDATE handler only refreshes `if TC2.playerTarget == unitTarget` (L1518-1523). The OnUpdate comment says the targettarget poll exists "because THREAT_LIST_UPDATE does not trigger for targettarget. Also the threat api only works in combat" (L1444-1446). [TC2 core.lua](https://github.com/dfherr/ThreatClassic2/blob/9f4a4c3592ef31f15e8ef1a4cb708d8bda3e2fbe/core/core.lua#L1440-L1580)
- **TC2 on Forever reads numbers**: `local isTanking, _, threatPercent, rawThreatPercent, threatValue = UnitDetailedThreatSituation(unit, TC2.playerTarget)` is followed by plain arithmetic: `rawThreatPercent / threatPercent > 1.2` (out-of-melee detection), `data.threatValue > 0`, and `floor(data.threatPercent + 0.5).."%"`. The bars are drawn with `bar:SetValue(data.threatPercent)` (core.lua L666-711, L416-434). The only secret checks are on the target *GUID*, used for TPS history: `issecretvalue(targetGUID)`, changelog v2.76 "implemented a TPS fallback if targetGUIDs are secret". The mob name is passed straight to SetText ("this also works with secret values on mainline", L775). [TC2 core.lua](https://github.com/dfherr/ThreatClassic2/blob/9f4a4c3592ef31f15e8ef1a4cb708d8bda3e2fbe/core/core.lua#L660-L712); [TC2 CHANGELOG](https://github.com/dfherr/ThreatClassic2/blob/master/CHANGELOG.md) (v2.73 "add support for WoW Forever and Retail (mainline)", v2.74 "use WOW_PROJECT_CAMELOT to identify WoW Forever")
- **Skada (Forever build)** guards every return: `local function readable(value) return value ~= nil and not issecretvalue(value) end`. It skips a unit if `raw` isn't readable and blanks scaled/rawPct/isTanking when they are secret. Its comment reads: "UnitDetailedThreatSituation returns raw threat plus the encoded percentages used by Forever's threat list; UnitThreatSituation only gives the percentage and leaves TPS/raw blank." It computes a pull line `me.value * 100 / me.scaled`, described as "the same line Forever's threat list displays" (Threat.lua L41-56, L141-170). The CHANGELOG says "Switched the Threat mode to native `UnitDetailedThreatSituation` data with raw threat values", and AGENTS.md says "TPS is not provided by the native threat API ... Target/focus tracking remains the trigger." [Skada Threat.lua](https://github.com/zarnivoop/skada/blob/1da7ee7d4144e25384f01bf80b8436e7afc6951c/modules/Threat.lua#L41-L170); [Skada CHANGELOG](https://github.com/zarnivoop/skada/blob/master/CHANGELOG.md)
- **Details Tiny Threat** calls `UnitDetailedThreatSituation(source, target)` with `target` = "target" or "focus". On Classic it divides threatvalue by 100 (L37-52). Its code has no `issecretvalue` checks, even though a Camelot TOC ships. [Details_TinyThreat.lua](https://github.com/Tercioo/Details-Damage-Meter/blob/2efa4b10628e0e4a91c346138cf8325e81d0a43c/plugins/Details_TinyThreat/Details_TinyThreat.lua)
- Value scale: TC2 and Details divide threatValue by 100 on Classic ("threat api uses 1 damage = 100 threat"). TC2 skips this on mainline/Forever: "mainline threat values are already 1 damage = 1 threat" (core.lua L688-691). [TC2 CHANGELOG_old v2.20](https://github.com/dfherr/ThreatClassic2/blob/master/CHANGELOG_old.md); [TC2 core.lua](https://github.com/dfherr/ThreatClassic2/blob/9f4a4c3592ef31f15e8ef1a4cb708d8bda3e2fbe/core/core.lua#L688-L691)
- Warcraft wiki: threat info for a unit/mob pair is only returned if the unit has threat against that mob, and temporary threat-reduction effects (Mirror Image, Fade) return 0. [API UnitDetailedThreatSituation](https://warcraft.wiki.gg/wiki/API:UnitDetailedThreatSituation)

### Inferences
- TC2 and Skada are both maintained and both ship Forever builds. Both treat `UnitDetailedThreatSituation(groupUnit, "target")` numbers as usable on Forever: TC2 without any guard, Skada with guards. TC2 names `targettarget` as the secret case. This conflicts with the user's premise that the numbers are secret in general. One explanation fits both: values are readable when the mob token is `"target"` (maybe also focus) and secret for derived or other tokens such as targettarget and possibly nameplateN. This should be tested in game before redesigning FireThreat. A quick check is `/run local a,b,c,d,e=UnitDetailedThreatSituation("player","target") print(issecretvalue(c),issecretvalue(e))` next to the same call with "nameplate1".
- If target-token values are readable, FireThreat could show exact numbers for the current target and use UnitThreatSituation status (plus SetValue on secret numbers) for the other nameplate mobs.

### Gaps
- No primary Blizzard documentation was found here that states which unit tokens make UnitDetailedThreatSituation return secret values on Forever. Other notes say the `forever` branch of wow-ui-source is where to check. TC2's comment and Skada's guards are indirect evidence only.
- Not verified whether UNIT_THREAT_LIST_UPDATE fires for nameplate tokens on Forever. Omen's "only target or focus" comment dates from 2008. TC2 filters on `unitTarget == playerTarget` and doesn't say.

## Q4: Each addon's data source, what it shows, and known limits

### Takeaway
Three eras: (1) vanilla/TBC 2005-2008, where the combat log was parsed with threat-coefficient tables and each player's numbers were broadcast over addon channels (KTM, Threat-1.0/2.0, Omen2); (2) WotLK 3.0+, Blizzard's threat API (Omen3 and everything since); (3) Classic 2019, a return to combat log plus sync (LTC2/TC2) until patch 1.13.5 re-enabled the API, then the API again. Every meter shows one mob's threat list across group members. Only the niche tank addons show one player's threat across many mobs.

### Cited Findings
- **KTM (vanilla 1.12)**, data source: own combat log parsing (KTM_CombatParser.lua, KTM_Regex.lua) plus addon-channel sync (KTM_Net.lua, KTM_NetIn.lua). Players without the mod are invisible. `/ktm` can list "These people aren't using KLHThreatMeter". Display: a raid table of each player's single total threat, plus a personal breakdown by source ("white damage, healing, mana gain ... Sunder Armor and Taunt"). Limits: no per-mob threat, so a master target is needed; "Taunt will only work properly when there is a master target". The taunt logic guesses the tank from `UnitName("targettarget")` (KTM_Combat.lua L396-440). [KTM Readme](https://svn.grimore.org/vanilla-wow-addons/k/KLHThreatMeter/Readme/Readme.txt); [Advanced Raid Commands](https://svn.grimore.org/vanilla-wow-addons/k/KLHThreatMeter/Readme/Advanced%20Raid%20Commands.txt); [KTM_Combat.lua](https://svn.grimore.org/vanilla-wow-addons/k/KLHThreatMeter/Code/KTM_Combat.lua); [file listing](https://svn.grimore.org/vanilla-wow-addons/k/KLHThreatMeter/Code/)
- **LibThreatClassic2 (Classic 1.13, 2019-2020)**, data source: COMBAT_LOG_EVENT_UNFILTERED in the class modules (ThreatClassModuleCore.lua L476, L678-706), NPC modules for boss mechanics, and addon comms (`SendComm(self:GroupDistribution(), ...)`, LibThreatClassic2.lua L1054-1061). It stores threat per player GUID per mob GUID: `GetThreat(player_guid, target_guid)` returns `threatTargets[player_guid][target_guid]` (L1276-1282). In principle that holds every mob, but the public API is unit-based and emulates Blizzard's: `ThreatLib:UnitDetailedThreatSituation(unit, target)` resolves `UnitGUID(target)` and derives the tank from `target .. "-target"`. Without targettarget it can only guess the tank from max threat, and "threatStatus 1 and 2 can't be determined" (L1646-1690). README: "This library is now obsolete and instead the ingame API can be used again." It also credits "Chris Heald and the Threat-1.0/Threat-2.0 teams". - **TC2 history**: v2.20 "Prepared the addon to use the threat api when available (from patch 1.13.5)" and "Removed the nameplate feature. ### Inferences
- FireThreat's model (one player's or group's status across many mobs, enumerated from nameplates) matches the tank-oriented multi-mob addons such as Lazy Threat and TankThreatTracker, not the classic meters. No mainstream meter offers an alternative way to enumerate mobs that would work on Forever. The combat log route (LTC2/KTM/TankThreatTracker's CLEU liveness check) is blocked there, so nameplate scanning, possibly plus target/mouseover, is what's left.
